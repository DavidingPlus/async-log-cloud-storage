# 服务端日志接入计划

## 目标与依据

服务端使用 dlog 异步记录启动、请求处理、异常和关闭信息，输出到轮转文件。计划基于 dlog `master` 的 v1.1.0（提交 `1b7187b`），并参考 [Kama 服务端](https://github.com/youngyangyang04/Kama-AsynLogSystem-CloudStorage/blob/main/src/server/Service.hpp)的请求、上传、列表和下载日志位置，结合本项目已有的异常处理与回滚流程实现。

## dlog 接入约定

- 先读取业务配置，再使用 `LogManager::GetInstance().buildLogger<RollFileFlush>()` 创建命名文件日志器。基路径由必填的 `log_file_base_path` 指定，默认配置位于可执行文件目录下的 `logs/server`；轮转大小先采用固定默认值，文件输出使用纯文本。
- `DLOG_INFO()` 等默认宏写入终端；业务文件日志使用 `DLOG_LOGGER_INFO(logger)` 等显式日志器宏。当前 dlog 没有日志等级过滤接口，第一版只添加需要保留的记录，暂不增加日志等级配置。
- `main()` 在读取配置后创建名为 `server` 的日志器，并保存在 `server/log.h` 声明的 `server::g_logger` 中；业务代码在初始化完成后使用，关闭日志系统后不再使用。
- 配置读取或日志器初始化失败时向 stderr 报告并以非零状态退出。日志器初始化成功后，数据准备及运行失败也记录到文件，并保留入口的 stderr 错误提示。
- 停止服务及所有日志生产者，完成业务资源清理并写出最后一条日志后，显式调用 `LogManager::Shutdown()`，等待排空并捕获后台输出错误。关闭失败使用 stderr 报告；关闭后不再使用 dlog。正常和异常退出均需执行关闭流程。
- 业务代码直接使用 dlog 日志宏；日志提交失败由 dlog 报告到 stderr。日志消息构造、格式化和访问日志器仍可能抛异常，需注意 `noexcept` 回调等边界。
- FATAL 与其他等级一样异步提交，不自动刷新或终止进程。正常关闭排空不保证崩溃时日志完整；后台输出失败后 dlog 放弃剩余待写数据，也不自动重试。

## 日志位置

| 位置 | 建议记录 | 级别 |
| --- | --- | --- |
| `src/server/main.cpp` | 配置成功后记录启动、数据目录准备、元数据恢复失败及原因、正常退出；配置读取失败输出 stderr | INFO / ERROR |
| `Service::run()` | 绑定成功后的监听地址和端口、事件循环退出；启动或运行异常在入口统一记录 | INFO / ERROR |
| `Service::GenericCallback()` | 非法 URI、未知路由、未处理异常及原因；HTTP 响应仍保持简洁 | WARN / ERROR |
| `Service::Upload()` | 成功时记录文件标识、存储类型、原始大小、实际存储大小和处理耗时；失败时记录原因，回滚清理失败单独记录 | INFO / WARN / ERROR |
| `Service::ShowFileList()` | 模板读取或页面生成失败由外层统一记录；暂不记录每次成功展示 | ERROR |
| `Service::Download()` | 记录已提交响应的文件标识、存储类型、状态码、字节数及处理耗时；记录文件缺失、目录不匹配、读取或解压失败 | INFO / WARN / ERROR |
| `DataManager` | 加载和持久化失败由调用方记录；临时文件清理失败单独报告 | ERROR |

400、404、409、413、416 等客户端可触发的结果记录简短原因，避免一律作为内部错误。上传查重时未找到元数据是预期分支，不记录为错误。异常在最终处理处尽量只记录一次，清理失败则另记。

文件名、路径及异常信息可能包含客户端控制的字符；写入前须转义或编码控制字符，防止伪造日志行。不记录文件正文、完整请求头或查询参数。下载日志只表示服务端已提交响应，不表示客户端已完整接收。处理耗时使用单调时钟计算。

## 实施顺序

1. **接入依赖。** 在 XMake 中为 Linux 服务端及相关测试接入 dlog 1.1.0，确认自有包仓库中的版本可用，验证 `fmt` 等传递依赖、构建及发布包运行依赖。
2. **建立生命周期（已完成）。** 先读取配置，再按配置创建命名文件日志器并启动服务；正常和异常路径完成清理后统一关闭日志系统，捕获并报告关闭错误。配置读取或日志器创建失败时通过 stderr 报告原因。
3. **接入业务代码。** 服务端使用同一个命名日志器；测试自行初始化和关闭，不依赖正式 `main()`。接入 HTTP 的 `noexcept` 边界、异常处理和清理流程时，考虑 dlog 的异常语义。
4. **补齐记录。** 先覆盖启动、监听、上传、下载、内部错误及关闭，再补常见请求拒绝与清理失败。上传成功日志在文件和元数据提交之后记录。
5. **验证并更新文档。** 扩展启动及服务端测试，检查启动、上传、下载、错误及 SIGINT/SIGTERM 正常退出后的尾部日志；验证重启后旧日志保留、日志目录不可写和可控的后台输出失败。覆盖业务清理失败，并确认原有 HTTP 响应、数据保护与回滚行为不变。验证安装包运行，更新 README 和开发计划。

日志写入失败的注入方式及对应测试以 dlog 和现有测试设施实际提供的能力为准；不得通过破坏已有数据来验证。
